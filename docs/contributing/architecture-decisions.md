# Архитектурные решения (ADR)

## ADR-001: Выбор usvg вместо roxmltree

### Контекст
Для парсинга SVG необходима библиотека, которая обрабатывает все особенности SVG формата: трансформации, градиенты, маски, стили, текст.

### Решение
Используем `usvg` как основной парсер, а `roxmltree` только как fallback.

### Обоснование
- **Полная поддержка SVG спецификации**: usvg реализует нормализацию SVG2, включая сложные фичи (маски, clipPath, маркеры)
- **Нормализация**: usvg приводит SVG к единому представлению, упрощая дальнейшую обработку
- **Безопасность**: usvg не выполняет произвольный код, в отличие от обработки CSS через js
- **Производительность**: usvg написан на Rust с оптимизациями, парсит большие файлы быстрее ручного обхода roxmltree

### Альтернативы
- **roxmltree напрямую**: требует ручной реализации всей SVG логики (трансформации, стили, градиенты) — слишком сложно
- **svgdom**: устаревший проект, не поддерживает современный SVG2

### Последствия
- Увеличивается размер WASM бинарника (~+500KB)
- Зависимость от C библиотек (fontconfig, freetype) при сборке с поддержкой текста

## ADR-002: Разделение промежуточного формата на 6 JSON файлов

### Контекст
Необходим формат для кэширования и передачи между крейтами. Варианты: один большой JSON или несколько разделенных файлов.

### Решение
Разделяем на 6 файлов: `meta.json`, `structure.json`, `geometry.json`, `styles.json`, `assets.json`, `content.json`.

### Обоснование
- **Разделение ответственности**: генератор может не читать geometry, если генерирует React компонент
- **Частичное кэширование**: при изменении стилей не нужно инвалидировать геометрию
- **Кэширование секций**: разные секции могут иметь разный TTL (meta — всегда, assets — редко)
- **Удобство отладки**: можно смотреть отдельные аспекты без лишнего шума

### Альтернативы
- **Один большой JSON**: проще, но любое изменение инвалидирует весь кэш
- **MessagePack/Protocol Buffers**: компактнее, но нечитаемые для отладки

### Последствия
- Сложнее реализовать атомарную запись (нужна согласованность 6 файлов)
- Больше файловых операций при чтении/записи

## ADR-003: Tera для шаблонизации

### Контекст
Генератору кода нужна система шаблонов для React, Vue, Vanilla и кастомных плагинов.

### Решение
Используем `tera` как движок шаблонов.

### Обоснование
- **Гибкость**: Tera позволяет переопределять блоки, что удобно для фреймворк-специфичных расширений
- **Наследование шаблонов**: можно иметь базовый шаблон и наследовать для React/Vue
- **Runtime компиляция**: плагины могут загружать свои шаблоны без перекомпиляции
- **Безопасность**: автоэкранирование по умолчанию

### Альтернативы
- **handlebars**: проще, но слабее система наследования
- **askama**: compile-time шаблоны, но плагины не могут добавлять свои шаблоны
- **rujukan**: быстрее, но меньше экосистема

### Последствия
- Runtime overhead на парсинг шаблонов (можно кэшировать)
- Зависимость добавляет ~1MB к размеру бинарника

## ADR-004: Модульная архитектура из 5 крейтов

### Контекст
Проект должен поддерживать CLI, WASM и библиотечное использование.

### Решение
Разделяем на крейты: `core`, `cache`, `generator`, `cli`, `wasm`.

### Обоснование
- **Разделение ответственности**: core не знает о файловой системе, generator не знает о CLI
- **WASM размер**: можно собирать только core + cache (memory) для браузера, исключая generator
- **Независимое тестирование**: каждый крейт тестируется изолированно
- **Параллельная разработка**: разные команды могут работать над разными крейтами

### Альтернативы
- **Монолитный крейт**: проще сборка, но сложнее поддерживать и тестировать
- **Разделение по фичам**: можно, но компилятор оптимизирует меньше

### Последствия
- Сложнее навигация по проекту (5 Cargo.toml)
- Нужен workspace для координации версий
- Публикация 5 крейтов в crates.io вместо одного

## ADR-005: Sled для дискового кэша

### Контекст
CLI нуждается в персистентном кэше между запусками. Варианты: SQLite, Redis, Sled, файлы.

### Решение
Используем `sled` как embedded KV-хранилище.

### Обоснование
- **Embedded**: не требует внешних зависимостей (в отличие от Redis)
- **Zero-config**: не нужно создавать схему (в отличие от SQLite)
- **Производительность**: ACID транзакции, асинхронность, сжатие
- **Подходит для CLI**: один файл кэша в ~/.cache/svg2web/

### Альтернативы
- **SQLite**: требует создания схемы и миграций
- **Redis**: требует внешнего процесса
- **Файлы (JSON)**: неэффективно для большого количества записей, нет индексов

### Последствия
- Зависимость добавляет ~1MB к бинарнику
- Sled не имеет встроенного TTL (реализуем на уровне приложения)

## ADR-006: Web Workers для WASM

### Контекст
WASM выполняется в main thread и может блокировать UI при обработке больших SVG.

### Решение
Проектируем API для работы в Web Workers, но не навязываем его в библиотеке.

### Обоснование
- **Неблокирующий UI**: парсинг 10MB SVG может занять 500ms, что блокирует рендеринг
- **Параллелизм**: можно обрабатывать несколько файлов одновременно
- **Изоляция**: ошибки в WASM не падают на main thread

### Альтернативы
- **WASM в main thread**: проще, но блокирует UI
- **OffscreenCanvas**: только для рендеринга, не для логики
- **SharedArrayBuffer**: сложнее, требует COOP/COEP заголовков

### Последствия
- Библиотека должна быть thread-safe (не использовать thread-local)
- Передача данных между потоками требует копирования или transferable objects
- StringPool становится критичным для больших данных

## ADR-007: Композитное кэширование (Disk + Memory)

### Контекст
Разные сценарии требуют разной стратегии кэширования: CLI нужен disk, WASM — memory, сервер — оба.

### Решение
Реализуем трейт `CacheBackend` и предоставляем две реализации: `DiskCache` (Sled) и `MemoryCache` (LRU). Композитный кэш пробует memory, затем disk.

### Обоснование
- **Гибкость**: WASM использует только memory, CLI использует disk + memory
- **Производительность**: hot cache в памяти, cold — на диске
- **Простота**: единый API для всех бэкендов

### Альтернативы
- **Только disk**: медленные повторные чтения в рамках одного запуска
- **Только memory**: нет персистентности между запусками CLI
- **Два независимых кэша**: сложнее управлять инвалидацией

### Последствия
- Нужно следить за консистентностью (версионирование ключей)
- MemoryCache нужно ограничивать по размеру (LRU)

## ADR-008: Версионирование ключей кэша

### Контекст
Изменение формата данных или логики парсинга должно инвалидировать старый кэш.

### Решение
Ключ кэша включает: `SHA256(svg) + версию крейта + хеш конфига`.

### Обоснование
- **Детерминизм**: одинаковый SVG + версия + конфиг всегда дают одинаковый ключ
- **Автоматическая инвалидация**: при обновлении крейта старые записи игнорируются
- **Безопасность**: SHA256 предотвращает коллизии

### Альтернативы
- **Только хеш SVG**: изменения в логике ломают кэш без инвалидации
- **Только версия**: разные SVG с одинаковой версией коллидят
- **Таймстемп**: недетерминировано

### Последствия
- Вычисление хеша добавляет overhead (SHA256 10MB SVG ~100ms)
- Версия крейта берется из env! во время компиляции

## ADR-009: Управление памятью в WASM через StringPool

### Контекст
WASM имеет ограничение в 2GB памяти, большие SVG могут вызвать OOM.

### Решение
Предоставляем `StringPool` для чанковой обработки больших строк.

### Обоснование
- **Предотвращение OOM**: строки не дублируются в памяти
- **Чанковая передача**: JS может передавать строку по частям
- **Явное управление**: вызывающий контролирует время жизни

### Альтернативы
- **Полагаться на GC**: WASM GC не оптимизирован для больших строк
- **Streaming API**: требует поддержки на уровне wasm-bindgen

### Последствия
- Усложнение API для работы с большими файлами
- JS должен явно освобождать память

## ADR-010: Conventional Commits для истории

### Контекст
Нужен единый формат коммитов для генерации changelog и семантического версионирования.

### Решение
Принимаем [Conventional Commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `docs:`, `refactor:`, `chore:`, `breaking:`.

### Обоснование
- **Автоматический changelog**: можно генерировать из коммитов
- **Семантическое версионирование**: `feat` → MINOR, `fix` → PATCH, `breaking` → MAJOR
- **Единый стандарт**: привычно для open-source сообщества

### Альтернативы
- **Свободный формат**: сложно автоматизировать релизы
- **Gitmoji**: менее формальный, сложнее парсить

### Последствия
- Требуется обучение контрибьюторов
- CI проверяет формат коммитов в PR
